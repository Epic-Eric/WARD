Technical Specifications and Implementation

Requirements Breakdown

The firmware stack is responsible for meeting the geometric and timing portions of the specifications. The current firmware already samples on a fixed angular lattice with 1.0 deg yaw spacing and 0.9 deg pitch spacing, and it already corrects the raw VL53L1X measurement for the sensor's 35 mm vertical offset and 34 mm forward offset before converting the hit to Cartesian coordinates. That matters directly for the 10 cm^2-at-2 m requirement, because at 2 m the spatial spacing is approximately Dx = 2000*tan(1.0 deg) = 34.9 mm and Dz = 2000*tan(0.9 deg) = 31.4 mm, so a 100 mm x 100 mm debris target spans about 2.9 x 3.2 samples and should be observed by multiple adjacent rays instead of a single marginal hit. To cover the full 1.22 m x 0.61 m roof section at a 2 m standoff, the commanded sweep must be at least theta_yaw = 2*atan(1.22/(2*2)) = 33.9 deg horizontally and theta_pitch = 2*atan(0.61/(2*2)) = 17.3 deg vertically. The existing 30 deg pitch span is sufficient, but the default 20 deg yaw sweep is not; the deployed cleaning cycle must therefore run with a configured sweep of at least 34 deg, not the current default. Meeting the under-2-minute cleaning-cycle specification also requires a serpentine pitch traversal rather than a reset-after-each-column raster, because the current geometry gives about 35 yaw columns x 34 pitch rows = 1190 samples for the required coverage.

The Control and Monitoring Interface stack is responsible for turning raw samples into a debris decision that can satisfy the 90%+ detection target across roof and debris variation. The current implementation is already structurally correct for that requirement: it stores a baseline scan, interpolates the baseline surface onto the current angular grid, computes foreground occlusion only where the current return is closer than baseline, and then clusters those foreground samples using spatial distance, yaw gap, pitch gap, and occlusion-consistency gates before applying debris heuristics. The key design decision is that detection is not based on raw point existence; it is based on residual foreground geometry relative to a roof-specific baseline, which is the correct way to stay robust to roof slope, shingles, and permanent fixtures. However, the current code drops very large clusters instead of classifying them as "too large to clear." To satisfy the alert requirement, the clustering stage should keep a second class of accepted detections where bbox diagonal, span, or occupied footprint exceeds the clearable envelope D_clearable, and that class should raise an alert instead of being silently rejected. The 90% requirement should also be validated against a labeled dataset grouped by roof type and debris type, because the current cluster score is only a ranking heuristic and not a calibrated probability.

The End-User Interface stack is responsible for satisfying the autonomy and operator-feedback requirements with no extra intervention after activation. The existing UI already has the correct control pattern for this: once a baseline exists, one monitoring command can start a scan, compare to baseline, rank clusters, and automatically issue MOVE_TO commands for each detected centroid while showing `clearing_debris_active` state and alert toasts. That is the right basis for O-1.3. The remaining implementation gap is that the current codebase has no explicit FIRE command path, only turret aiming. To satisfy the "send fire command has visual feedback" requirement, the control server should expose a clearing state machine such as `aiming -> firing -> fired -> fault`, driven by explicit firmware acknowledgements, and the UI should bind that state to the existing toast/banner components. In the same way, the oversized-debris path should surface as a dedicated alert state rather than only as an absence of auto-clear behavior.

Implementation

The detection math should remain baseline-relative. For each pose (yaw, pitch), the server should evaluate occlusion as delta_occ = d_base - d_curr and keep a sample only when d_curr < d_base and delta_occ > tau, where tau is the roof-specific residual tolerance. The current interpolation design is appropriate and should be preserved: when there is no exact baseline sample at a pose, estimate the baseline range with inverse-distance weighting on the angular grid, d_hat = sum(w_i*d_i)/sum(w_i), with w_i = 1/max(rho_i, 0.15)^2 and rho_i = sqrt((Delta yaw / Delta yaw_step)^2 + (Delta pitch / Delta pitch_step)^2). This is the correct design choice because it avoids false residuals caused by missing rays while still preserving local surface shape. After residual extraction, the cluster acceptance logic should continue to enforce local support, minimum multi-angle occupancy, and occlusion-depth consistency, because those constraints are what separate real debris from isolated noise. The current debris score can remain a prioritization metric, score = 100*(0.34*max_component + 0.24*mean_component + 0.22*count_component + 0.10*occupancy_component + 0.10*compactness_component), but that score should not be used as proof of the 90% requirement; the requirement is met only after threshold tuning and validation on held-out captures.

The clustering equations should also be stated explicitly. Two residual samples p_i = (x_i, y_i, z_i, yaw_i, pitch_i, delta_i) and p_j = (x_j, y_j, z_j, yaw_j, pitch_j, delta_j) are connected only if all of the following are true: d_3D(i,j) = sqrt((x_i-x_j)^2 + (y_i-y_j)^2 + (z_i-z_j)^2) <= r_pair, |yaw_i-yaw_j| <= Delta_yaw,max, |pitch_i-pitch_j| <= Delta_pitch,max, and |delta_i-delta_j| <= Delta_occ,max. Here r_pair is distance-scaled from the measured range and then clipped between configured minimum and maximum radii. After that neighbor graph is built, the implementation performs a DBSCAN-like expansion in which a point is a core point only if it has at least MinPts supported neighbors, and a cluster is accepted only if point_count >= N_min, unique_yaws >= Y_min, unique_pitches >= P_min, mean(delta_occ) >= delta_mean,min, max(delta_occ) >= delta_max,min, occupancy = point_count / (unique_yaws*unique_pitches) >= eta_min, and bbox_diagonal <= D_max. Writing the math this way makes it clear that the detector is based on geometric consistency, not just point density.

The geometry and aiming math should be treated as calibration-critical, not hard-coded forever. The firmware currently converts raw range to axial range with R_axial = sqrt(d_raw^2 + 35^2) + 34 and corrects pitch with pitch_true = pitch_motor - atan(35 / d_raw). The auto-clear aim path currently computes yaw = atan2(y, x) and pitch_motor = atan2(z, sqrt(x^2 + y^2)) + atan(13 / sqrt(x^2 + y^2 + z^2)). Those equations are the correct form for the current turret layout, but the constants 35 mm, 34 mm, and 13 mm must be calibrated from the physical build and then verified by scanning a flat reference plane and minimizing plane-fit residual thickness after transformation. In practice, the acceptance criterion should be that the same flat roof surface produces a thin, repeatable baseline sheet rather than a doubled or tilted cloud. The turret zero position also has to be calibrated so that commanded 0 deg yaw and the reference pitch angle correspond to the actual roof frame; otherwise even correct range math will create systematic baseline-current mismatch.

The parallax-correction equations should be written explicitly for both sensing and clearing. For sensing, let h_s be the sensor height above the pitch axis and f_s be the sensor face offset forward of the axis. Then the raw reading d_raw is converted to axis-centered range by R_scan = sqrt(d_raw^2 + h_s^2) + f_s, and the true beam angle is theta_true = theta_motor - atan(h_s / d_raw). For clearing, let h_l be the laser height above the same pitch axis. If the target centroid in the robot frame is (x,y,z), then yaw_cmd = atan2(y,x), theta_true,target = atan2(z, sqrt(x^2+y^2)), R_target = sqrt(x^2+y^2+z^2), and the commanded laser pitch is theta_laser = theta_true,target + atan(h_l / R_target). This sign difference is important: the sensor correction subtracts the vertical offset to recover the true measured point, while the laser correction adds the offset so the fired beam lands on the desired target point. Those equations are what should be calibrated experimentally from the real mount geometry.

The timing design must explicitly support the 1.22 m x 0.61 m in under 2 minutes requirement. For the required 34 deg horizontal sweep, the current angular grid gives N_yaw = 35 and N_pitch = 34, so N = 1190 samples. Using the present 80 ms settle delay and an estimated 15 ms single-step pitch motion at 20 rpm, a serpentine scan is approximately T ~= N*(0.080 + 0.015) + (N_yaw - 1)*0.045 = 114.6 s, which fits under 120 s before network and clustering overhead. A reset-to-start pitch scan at every yaw column adds about 34*0.495 = 16.8 s of retrace time and pushes the cycle beyond the limit. The specific implementation decision is therefore to switch the firmware scan loop to boustrophedon motion, keep the current angular resolution, and reserve the server-side clustering for lightweight post-processing after capture completion. This preserves the 10 cm^2 detection granularity while keeping the cleaning cycle inside the timing budget.

The calibration and verification plan for the specifications should be explicit. First, collect repeated clean-roof baseline scans for each roof type and set tau from the clean residual distribution, for example tau = max(25 mm, mu_clean + 3*sigma_clean), so the tolerance is tied to observed roof noise rather than guesswork. Second, place labeled debris objects spanning the required debris-size range and compute Accuracy = (TP + TN)/(TP + TN + FP + FN) separately for each roof family and for the pooled dataset; the release criterion should be >= 90% on every roof/debris subgroup, not only on the aggregate. Third, define a clearable footprint threshold D_clearable from the actual clearing mechanism and classify any cluster with bbox span or diagonal above that threshold as `oversize_alert` instead of `auto_clear`. Fourth, add explicit command acknowledgement for the fire action so the UI can display "aiming," "firing," "fired," or "fault" states with no extra user input. That closes the remaining gap between the current codebase and the full specification set.
